# Recruitment & LFG

Finding players is a matching problem, and most matching systems solve it badly — with ratings, metrics, and optimization language that turns tables into products and applicants into profiles. Esiana's recruitment is built on the opposite premise: help players understand the table, not evaluate the GM. Everything on a listing exists so a stranger can answer one question honestly: is this my table?

## How it works

A recruiting campaign publishes a public lobby page: tagline, premise, table style, schedule, seats available, and the documents that define the table's culture — expectations, rules, safety guidelines, session-zero notes, homebrew, character creation, FAQ. The GM chooses which documents to expose, written as ordinary wiki pages, and applicants read them under a "before you apply" section before committing. A short vibe-disclosure note near the apply button says out loud what listings usually hide: tone, pacing, energy, the kind of evenings these actually are.

Applying is a conversation starter, not a transaction. The applicant writes an introduction — who they are, why this table — and the GM reviews applications with organizer-only context like timezone and schedule overlap. Accepting adds the applicant to the campaign; declining can carry a canned reason (schedule mismatch, table full, playstyle fit) plus a short personal message, delivered to the applicant with that context. Seats and player caps are enforced, so an accepted applicant never overflows a full table.

Several things are deliberately absent. There are no ratings, no leaderboards, no match scores, no public application counts, no attendance percentages, no retention badges. The lobby shows open seats and schedule context — never how many applied or how "reliable" anyone is. Descriptions stay descriptive ("ongoing since May, session 38, two spots open") and never evaluative ("high retention, reliable DM"). This is a design position, not an oversight: tables are collaborations, and recruitment copy should inform self-selection, never rank people.

## Using recruitment

As a GM filling seats, work through it in order:

1. In Campaign Settings → Recruitment, turn on looking-for-group. A campaign that is not flagged never appears in the directory, no matter how complete its page.
2. Write the listing top-down: tagline first (one line that survives scanning), premise second (the actual fantasy), then the vibe note — tone, pacing, energy — near the apply button.
3. Fill the schedule honestly: frequency, day, time, timezone, session length. Most failed applications die on schedule, so precision here saves everyone's time.
4. Select table preferences (experience level, age range, language, seat counts) and safety tooling (safety tools in use, content warnings, external tools like the VTT). These are filters applicants actually use.
5. Choose which wiki documents to expose — table expectations, rules, safety guidelines, session zero, homebrew, character creation, FAQ. Write missing ones as wiki pages first; the listing can only expose what exists. Prefer the canonical page titles ("Table Expectations", "Session Zero") so imports and theme packs keep working.
6. Review applications as they arrive. Check the organizer context, accept the fits, and decline the rest with a reason — a two-line decline with a real reason is part of running a table people recommend.

As an applicant, read before you write. The premise tells you the fantasy, the schedule tells you the commitment, the expectations and safety documents tell you the culture, and the vibe note tells you the evenings. Then introduce yourself like a person: who you are, what you want from this table, and anything logistical (timezone, availability gaps) the GM needs. There is a recruitment pitch in your user settings that pre-fills applications — set it once and stop retyping it.

## Campaign configuration

Recruitment lives in Campaign Settings → Recruitment, organized so each workflow gets attention separately: the listing itself (identity, pitch, exposed documents), the schedule, table preferences, safety and tools, and the applications queue. A status block at the top shows at a glance what is configured and what still needs setup — schedule missing, safety unset, identity incomplete — because half-finished listings attract nobody. Turning looking-for-group off unlists the campaign immediately; existing members and applications are unaffected.

Genre themes come from a shared catalog plus optional custom tags, and game system from the system picker — both descriptive metadata for discovery, neither affecting how Esiana behaves. Content warnings and safety tools use plain text plus a safety glossary with in-app help, so write them for humans, not for a form.

## Players

If you are looking for a table, the directory is browsable without an account; applying requires one. Read listings completely before applying — GMs notice who read the expectations doc, and the decline reasons you avoid are schedule mismatch and playstyle fit, both preventable by reading. If you are declined, the reason (when the GM provides one) arrives with the notification; tables fill for ordinary reasons, and a declined application is not a verdict.

## Things to know

A public listing is genuinely public: premise, schedule, seats, and exposed documents are visible to guests, so never put secrets, addresses, or anything you would not post on a forum in a listing or an exposed document. Invite links and recruitment are independent systems — a private table can recruit publicly while onboarding by link, and rotating an invite link affects links, not listings. Join requests are rate-limited against spam, so rapid-fire applications will throttle. And notifications do the quiet work: GMs are told of new applications, applicants are told of decisions — check notification preferences if either side goes silent.
